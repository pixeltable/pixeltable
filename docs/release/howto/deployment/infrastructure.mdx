Put `TableModel` classes and `FastAPIRouter` in `app.py`. The file has to
sit under a project root. `pxt init` writes `pixeltable.toml`, or appends
`[[tool.pixeltable.database]]` to an existing `pyproject.toml`. Schema and
service refuse a file with no project root.

<Tree>
  <Tree.Folder name="proj" defaultOpen>
    <Tree.File name="pixeltable.toml" />
    <Tree.File name="app.py" highlight />
    <Tree.File name="functions.py" />
  </Tree.Folder>
</Tree>

`pixeltable.toml` makes `proj` the root. `app.py` imports as `app`.
`from functions import excerpt` works because `functions.py` is a sibling.
A nested file (`ads/app.py`) imports as `ads.app`. Every directory name
on that path has to be a Python identifier. `pxt init` reports names that
are not.

A `pyproject.toml` is a project root only if it has `[tool.pixeltable]`.
If both files sit in the same directory, `pixeltable.toml` wins. `pxt init`
writes one or the other, not both. Nested `pxt init` is refused: one
project, one root.

Apply, then serve:

```bash
pxt schema update app.py my_app
pxt service update app.py my_app
```

`my_app` is a catalog directory, not a folder on disk. A second
application file is another path under the same root, applied to another
catalog target:

```bash
pxt schema update ads/app.py ads
pxt schema update docs/app.py docs_app
```

A second database is another `[[pixeltable.database]]` entry, not a
folder. The local entry is unnamed (`local`). A hosted one is named by
its `pxt://org:db` URI and carries what `pxt db update-runtime` packs:

```toml
[[pixeltable.database]]

[[pixeltable.database]]
name = "pxt://org:prod"
include = ["app.py", "functions.py"]
```

Same file, different TARGET:

```bash
pxt schema update app.py my_app
pxt schema update app.py pxt://org:prod
```

Mount the same router on an existing FastAPI app:
[HTTP serving](/howto/deployment/serving). Do not run `python app.py`.

UDFs are recorded as a module path relative to the project root.
[Custom functions](/platform/custom-functions). `return_rows=True`:
[HTTP serving](/howto/deployment/serving#return-computed-columns).
Apply schema once before starting workers.

## Where files live

Default home is `~/.pixeltable`: `pgdata` (PostgreSQL), `media` (generated files), `file_cache` (downloads). `pxt.create_dir` is a catalog namespace, not a folder on disk.

- Inserted local files: the path is stored; the original stays put.
- Inserted URLs: the URL is stored; first access downloads into the file cache.
- Generated media: written to the media store (local, or `destination=` / `PIXELTABLE_OUTPUT_MEDIA_DEST`).

File cache size is `file_cache_size_g` in `config.toml` only. [Configuration](/platform/configuration).

```toml
# ~/.pixeltable/config.toml
file_cache_size_g = 50
```

With no HTTP, storage can be ephemeral; `export_sql` the result. [Self-hosting](/howto/deployment/overview). A long-running service needs a persistent volume at `PIXELTABLE_HOME` (pgdata, media, file_cache). Starter-kit Dockerfiles set `PIXELTABLE_HOME=/data/pixeltable`.

```bash
PIXELTABLE_INPUT_MEDIA_DEST=s3://your-bucket/input
PIXELTABLE_OUTPUT_MEDIA_DEST=s3://your-bucket/output
```
