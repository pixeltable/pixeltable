Pixeltable is an open-source Python framework for AI apps that work on video, images, audio and documents. Your files live in tables, next to ordinary columns. The work you want done on them, like sampling frames, transcribing audio, calling a model or embedding the result, is a column too. Insert a row and Pixeltable runs that work, stores what it produces and updates the search index. The whole backend, from tables to HTTP routes, sits in one Python file, `app.py`.

## The stack it replaces

Take a video search app. Users upload videos, each one gets transcribed and summarized, and you can search the summaries. Built the usual way, that's:

- an S3 bucket for the videos, and a Postgres table for their keys and metadata
- a queue or an Airflow DAG that picks up new uploads, extracts the audio, and calls Whisper and then an LLM
- a job that embeds the summaries and writes them to a vector database
- a FastAPI app that takes uploads, queries Postgres and the vector database, and merges the results
- the scripts in between that keep all of it in sync

Each piece is fine on its own. The trouble is the joints. A video gets deleted from the bucket and its row stays behind. The DAG reruns every video because it can't tell which ones changed, unless you write that bookkeeping yourself. The vector database keeps serving embeddings of last week's summaries. And the first time you want to try a better prompt, you write a backfill script and hope it touches the right rows.

In most of these projects, the plumbing is most of the code, and it's where most of the bugs are.

## The same app in Pixeltable

Each of those systems becomes a few lines of `app.py`:

| Before | In `app.py` |
|---|---|
| The bucket and the metadata table | A table with a `video: pxt.Video` column |
| The DAG steps | Computed columns: `audio`, then `transcript`, then `summary`, each one reading the one before |
| The embedding job and the vector database | `pxt.EmbeddingIndex(summary, ...)` in the table's `__indexes__` |
| The FastAPI app | A `FastAPIRouter` with an insert route and a search route |
| The sync scripts | Nothing to write. Inserting a row runs everything that depends on it |

The full file is in the [README](https://github.com/pixeltable/pixeltable#what-it-looks-like). Two commands run it: `pxt schema update app.py my_app` creates the table and its index, and `pxt service update app.py my_app` starts the service. The [Quickstart](/overview/quick-start) walks through both with a smaller file.

## What a change costs

Every computed column refers to the columns it reads, so Pixeltable knows what to run and, after a change, what to rerun. That's the part you'd otherwise build by hand.

New uploads only cost new work. Add 100 videos today and those 100 get processed. The thousands from last week aren't touched.

Say the summaries are too long. You edit the prompt in `app.py` and run `pxt schema diff app.py my_app`, which tells you the summary column will change and that existing values won't be recomputed. `pxt schema update` applies it, and once `pxt service update` restarts the service, new uploads get the new prompt. When you like the results, `pxt recompute my_app/videos summary` redoes the old summaries and the index entries built from them. The transcripts stay as they are, so you don't pay for Whisper twice.

Failed model calls and table versions follow the same bookkeeping. [When computed columns run](/overview/how-it-works#when-computed-columns-run) has the details.

The same `app.py` runs on [Pixeltable Cloud](/cloud). `pxt db update` uploads the project to a hosted database, then the same two commands take its `pxt://` URI in place of `my_app`, so moving isn't a rewrite.

## Why we built it

We're database people: Pixeltable comes from the creators of Apache Parquet and Impala. When we looked at multimodal AI projects, we kept finding the same thing. The models were the interesting part, and the team spent most of its time on data plumbing.

Lovable and Bolt made web apps easy to build by putting a small surface over a hard problem. We wanted that for developers working with video, images, audio and documents, so we moved the work into the database. The engine tracks what depends on what, so it works out which rows to recompute. The first version of an app and its tenth revision are the same kind of work: edit `app.py`, run `pxt schema update`, then `pxt service update`.

One file also helps when a coding agent writes the code. The agent writes the whole backend in `app.py`, and you review one diff instead of a change in every system. [AI coding agents](/overview/building-pixeltable-with-llms) covers the skill and the MCP servers.

The longer version is in [Making Multimodal More Lovable](https://www.pixeltable.com/blog/making-multimodal-more-lovable).

## When it's the wrong tool

If you don't want a schema, Pixeltable is the wrong tool. Every column has a type, and the shape of every table lives in `app.py`.

It isn't a no-code builder either. You write Python, and Pixeltable is the data layer under your app. The frontend is up to you, whether that's Lovable or your own React code calling the routes from its server.

It won't pick your model or tell you whether the answers are any good. Video files are still big and model APIs still fail. What Pixeltable does is keep track of what ran and what needs to run again.

And if your current stack works and the glue isn't costing you much, keep it.

If you try Pixeltable and leave, your data comes with you. Media can live in your own bucket ([Cloud storage](/integrations/cloud-storage)), and `pxt.io.export_sql()` or `pxt.io.export_parquet()` copies a table out whenever you want.
