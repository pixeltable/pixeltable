Pixeltable stores images, video, audio, documents, and ordinary columns in tables you declare in Python. Tables, computed columns, indexes, and HTTP routes live in **one Python file** (`app.py`).

On this machine you create those tables with `pxt schema update`. Start HTTP with `pxt service update` if you want it, then insert rows from Python, the dashboard, or POST. The same `app.py` can target [Pixeltable Cloud](/howto/deployment/cloud) after you set `PIXELTABLE_API_KEY` and run `pxt db update`. That Cloud command creates or updates the hosted database. It does not insert rows and does not start app HTTP.

Most stacks glue a blob store, a warehouse, a vector database, an orchestrator, and custom endpoints. Each transform and index in Pixeltable is a column on the same table as the data. Insert a row. Transforms run. Indexes stay current.

## What you declare

A `TableModel` class becomes a table when you run `pxt schema update`. An annotation (`title: pxt.String`) is a stored column: the value you insert. An assignment (`title_upper = ...`) is a computed column. It runs on insert and on update. An embedding index lives on the model, so new rows are searchable without a separate vector database. A `FastAPIRouter` in the same file defines HTTP routes, for example POST a row and get computed columns back.

HTTP is optional. You can run `pxt schema update`, insert from Python, then export. Views, UDFs, versioning, and import/export start in the [User Guide](/platform/type-system).

Notebooks and tests can still call `pxt.create_table()`. An app declares tables in `app.py`.

## What this replaces

- **One catalog** for images, video, audio, documents, and ordinary columns
- **Transforms as columns**: incremental, not a pipeline you re-run
- **Indexes that follow the data**: embeddings stay in sync with the rows
- **HTTP from the same file**, or skip HTTP and insert from Python

Coming from Pinecone, LangChain, or hand-rolled FastAPI? See [Migrate](/howto/coming-from).
